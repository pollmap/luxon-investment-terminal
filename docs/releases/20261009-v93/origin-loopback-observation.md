# v93 원점 내부 지연 관측

**공개 인터넷을 제외한 내부 경로에서도 약 1.9초 p95가 관측됐습니다. 네트워크 거리만으로 전체 지연을 설명할 수는 없습니다.** 다만 이 시험의 부하 발생기도 API 컨테이너에서 실행됐으므로 CPU 제한의 영향을 서비스 단독 원인으로 확정하지 않습니다.

## 범위와 조건

- 버전 `20261009-first-interaction-v93`, 부하 구간 **10/9 02:20:18~02:20:22 KST**.
- **총 100건·동시 100건·한 배치**입니다. 검색 50건과 상세 요약 50건을 섞었습니다. 각 종류별 동일 10개 검색어·종목을 5번씩 사용했습니다. 추가 공개 WAN 시험은 하지 않았습니다.
- 경로는 API 컨테이너 내부 **`http://127.0.0.1:8210`**, HTTP/1.1, 최대 연결 100개입니다. Nginx·TLS·Cloudflare·공개 인터넷은 우회합니다.
- 요청 헤더는 `Accept-Encoding: gzip`입니다. 앱 `Server-Timing: app;dur`를 읽고, Nginx의 `X-Market-Cache`는 없는 경로입니다.
- 기존 실행 상태에서 캐시를 비우거나 예열하지 않았습니다. 따라서 이번 배치를 cold/warm으로 단정하지 않습니다. 공급자 직접 호출·설정 변경·코드 변경은 하지 않았습니다. 조회에 따른 기존 요청 큐 기록은 허용했습니다.

각 타이밍의 p95는 독립 집계입니다. p95끼리 빼서 특정 계층의 시간으로 계산하지 않습니다.

## 같은 시점의 자원·DB

- 약 2.216초 관측 창에서 API cgroup CPU 사용량은 2.962 CPU초였습니다. 제한 발생 횟수는 **14회**, 제한 시간 증가는 **418,922μs**입니다. CPU 한도는 `150000/100000`, 즉 1.5 CPU입니다. **부하 클라이언트·DB 상태 검사도 같은 cgroup에 포함**되므로 이 증가를 API 처리만의 비용으로 보지 않습니다.
- 호스트는 논리 CPU 4개입니다. 약 4초 창 전체 사용률은 I/O 대기를 제외해 **66.84%**, I/O 대기는 **4.04%**였습니다. 다른 서비스와 이번 검증 프로세스가 포함됩니다.
- 부하 중 **02:20:20 KST의 DB 단일 관측**에서 막힌 연결은 0개였습니다. 별도 연결 1개 active, 5개 idle, 1개 idle in transaction이며 idle 대기는 ClientRead였습니다. 한 번의 관측으로 잠금·쿼리·DB I/O 병목이 항상 없다고 판단하지 않습니다.
- 수집은 계속 진행 중이었습니다. 마지막 진행시각 02:19:29, 종목 003030의 신용 수집, attempts 54,887·cursor188입니다. 이 사실만으로 수집기가 조회 지연을 유발했다고 단정하지 않습니다.
- 부하 후 **02:21:34 KST의 별도 단발 관측**은 API CPU 24.61%·메모리605.8MiB/1.25GiB, worker CPU83.35%·메모리710MiB/1.5GiB였습니다. 부하 구간 측정치와 섞지 않습니다. 최초 Docker stats 요청에는 유지 중인 DB 컨테이너 이름이 잘못 들어가 실패했으며, API·worker만 대상으로 이 상태 관측을 보완했습니다. HTTP 부하는 반복하지 않았습니다.

## 이미 시행한 공개 시험과의 관계

부모 작업에서 시행한 공개 HTTP/2 시험 (로컬 보존 자료: `public-http2.json`)은 Windows PC에서 TLS 연결 하나·동시 스트림100개, 경로별 100건씩 실행했습니다. 이번 혼합 HTTP/1.1 100건과 조건이 다릅니다.

공개 결과에서 `warm`이라는 이름도 모든 응답이 캐시 적중했다는 뜻은 아닙니다. 검색 warm 300건은 HIT200·EXPIRED100, 요약 warm은 HIT140·EXPIRED160이었습니다. 검색 first도 MISS10·HIT90이며 완전히 빈 캐시 조건은 아닙니다.

관측 근거는 **앱 타이밍 자체의 증가와 내부 경로의 지연, CPU 제한 발생**입니다. 가능한 원인 후보는 앱 요청 대기·공유 결과 생성·캐시 만료 시 동시 처리·CPU 할당이지만, 이번에는 각 후보의 시간을 분리하지 않았습니다. DB 연결 대기·직렬화·웹 전달 경로 중 어느 하나를 원인으로 확정하지 않습니다. 다음 원인 분리를 한다면 부하 발생기를 API cgroup 밖에 놓는 조건부터 맞춰야 합니다.

증거: origin-loopback-observation.json (로컬 보존 자료: `origin-loopback-observation.json`). 추가 코드·설정·서버 변경 없이 종료했습니다.
