# v49 — 전 종목 수집의 중복 대기 제거

공개 버전 `20261004-toss-pacing-v49`. v48a 기업행사 파서, 기존 프런트·DB·공개 주소·사용자 설정과 다른 VPS 서비스를 유지했다.

## 현재 상태를 다시 확인한 결과

2,875종목 대상 작업 진행은 49,576회, 종목 커서 2,299이었다. 일봉 작업 상태는 collecting 2,680, ready 84, error 109, no_data 1. 나머지 과거 수급·프로그램·공매도·신용·대차·원주가에도 수집 중 작업이 많았다. ready/no_data는 개별 자료 작업의 상태이며 종목 전체 완료가 아니다.

일봉 collecting 2,680건 모두 과거 조회 커서가 있었다. 원주가의 커서 없는 1건은 실제 저장 자료가 이미 완료되고 큐 상태가 아직 반영되지 않은 사례였다. 따라서 과거 커서가 대량 소실됐다고 단정하거나 초기화하지 않았다.

## 변경

TossClient가 그룹별 응답 완료 시점에 0.5초 간격을 더해 다음 요청을 대기시키고 있었다. 기본 설정에서 응답이 0.8초이면 다음 요청 시작까지 1.3초가 걸리는 구조였다.

요청 시작 시점을 기준으로 그룹별 간격을 적용했다. 느린 응답은 이미 해당 간격을 소비하고, 빠른 응답만 남은 시간을 기다린다. 그룹별 직렬 호출·공유 인증·최소 간격·429 Retry-After·401 토큰 재발급은 유지했다. 새 수집 프로세스나 동시 호출을 추가하지 않았고 계정의 요청 한도를 높이지 않았다.

내부 API 상태에 request_group / upstream_ms / budget_wait_ms / pacing_version을 기록하여 통신 시간과 호출 예산 대기를 분리했다. 토큰·키·인증 헤더를 기록하지 않는다. 원본 응답·자료 커서·정규화·자료 해석에는 변경하지 않았다.

## 검증

- 관련 토스·시장·과거 수집 검사 58개 통과.
- 가상 시계로 긴 응답 0.8초 → 다음 시작 간격 0.8초, 짧은 응답 0.1초 → 시작 간격 0.5초 검증.
- 429 응답에 Retry-After 2초가 있으면 응답 종료부터 2초를 지킨 뒤 재시도 검증.
- 공개 v49 health 정상, 기존 수집 작업자가 실제 요청을 이어가는 것을 확인했다.
- 실제 수급 응답 985~2,946ms 관측에서 budget_wait_ms=0. 캔들 응답 274.72ms에서 budget_wait_ms=201.11. 이는 마지막 요청 관측값이며 평균·p95 또는 전후 비교 성능시험이 아니다.
- 실제 큐 시도 49,594회, 커서 2,302로 전진. 기존 과거 조회 커서와 순환 진행을 초기화하지 않았다.

근거: `work/remaining-v49/before.json`, `cursors-before.json`, `tests.xml`, `actual.json`, `public.json`. 명세의 페이지 제한도 재확인했으며 캔들 최대 200개·수급 최대 100개를 넘겨 호출하는 변경은 하지 않았다. 공식 명세: https://openapi.tossinvest.com/openapi-docs/latest/openapi.json .

## 남은 완료 기준

중복 대기를 제거했다고 전 종목 과거 수집이나 공개 웹 100동시 응답 목표가 완료된 것은 아니다. 전체 과거/404, TTM/분할, 배당 기업행사·재투자, 실제 장중 스트림 검증, 공개 성능 목표 및 아버님 실사용은 남았다. 인터넷 검색·상세 p95는 이번 수정에서 재측정하지 않았으며 기존 미달 상태를 유지한다. 증권사 수집 속도와 사용자 HTTP 조회 성능은 별도 검증한다.
