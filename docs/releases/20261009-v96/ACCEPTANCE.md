## 공개 성능 — 100 동시 HTTP/2 스트림

Windows PC 공용 인터넷, HTTP/2 TLS 연결 하나, 검색어 10개·종목 10개입니다. 최초 100회·후속 300회·1.6초 후 100회를 구분했습니다. API 프로세스 밖에서 수행했으며 수집기는 계속 실행했습니다. 독립 연결 100개 시험은 아닙니다.

| 경로 | 첫 구간 p95 | 후속 p95 | 1.6초 후 p95 | 오류 |
|---|---:|---:|---:|---:|
| 검색 | 1,195ms | 840ms | 1,255ms | 0/500 |
| 상세 요약 | 571ms | 290ms | 1,110ms | 0/500 |

후속 상세 300회는 모두 Nginx HIT였습니다. 검색의 후속 구간에는 만료 응답 100회가 포함됐습니다. 따라서 290ms만으로 전체 상세 목표 달성이라고 판단하지 않습니다. 캐시 만료 상태와 검색은 여전히 목표 미달입니다.

Nginx cache-lock 1초/100ms를 한 번 비교했습니다. 따뜻한 상태에서는 100ms가 유리한 구간이 있었지만 새 버전의 최초 요청에서는 검색 MISS 82회·상세 MISS 73회로 중복 upstream 요청이 늘었습니다. `proxy_cache_lock_timeout`은 1초로 복구했습니다. 시세 캐시 유효 기간을 늘리거나 만료 자료를 최신으로 바꾸지 않았습니다. 실험과 관측 상태가 다른 결과로 전체 속도 개선 배율을 만들지 않습니다.

## 이어서 수행할 작업

1. 만료 요청의 공통 revision 읽기를 하나로 묶고 실제 공개 경로를 재측정합니다.
2. 반복되는 시계열 출처 JSON은 읽기 호환 배포 후 공유 저장을 활성화합니다. 원문·정정·기존 행을 대량 삭제하지 않습니다.
3. 최초 주식단위 검토와 필요한 XBRL 입력 작업을 연결합니다. 실제 근거가 없는 TTM은 계속 차단합니다.
4. Cloudflare 정적 화면은 직접 공개 API를 조회하도록 연결해 동적 Worker 경유 지연과 무료 호출 예산을 줄입니다. 기존 주소·CSV POST·WebSocket을 보존합니다.
