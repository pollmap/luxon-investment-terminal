# v132 공개 100연결 성능 관찰

2026-10-11 KST. **검색 p95 300ms·상세 요약 500ms 목표는 두 시험 모두 통과하지 못했습니다.** 수집을 멈춘 시험에서도 DB 단계와 앱 밖 수신 지연이 나타났습니다. 따라서 수집기만 원인이라고 판단하거나, 플랫폼을 이전하면 해결된다고 결론 내리지 않습니다.

## 측정 범위와 조건

| 시험 | 시작 시각 | 운영 조건 | 근거 |
|---|---|---|---|

| 수집 중지 시험 | 22:31:16 KST | 작업 담당자가 수집 중지 후 실행. JSON 자체는 수집기 상태를 증명하지 않음 | [원본](public-100connections-worker-off.json) |

Windows PC의 공개 인터넷에서 HTTP/2 연결 100개를 각각 만들고 연결당 한 요청씩 보냈습니다. 검색과 상세 요약 각각 최초 100건, 후속 3회 합계 300건, 1.6초 대기 후 100건을 측정했습니다. 시험당 1,000건 모두 응답 검증을 통과했고 오류는 0건입니다.

- DNS·TCP·TLS 연결 준비는 요청 지연에 포함되지 않습니다. 연결은 시험 안에서 재사용했습니다.
- 두 시험의 전송 방식·요청 헤더·동시 요청 수는 같습니다. 서로 다른 `cache_probe`를 사용한 순차 관찰이며 캐시 이력·주변 부하가 완전히 통제된 A/B 시험은 아닙니다.
- `first`는 완전한 콜드 캐시를, `warm`은 캐시 HIT를 보장하지 않습니다. 원본의 실제 Nginx 캐시 헤더로 구분합니다.
- 브라우저 검색·차트 렌더링·사용자 동선·LCP·INP·CLS 시험이 아닙니다.
- 앱 시간은 응답 헤더까지입니다. 프록시·전송·클라이언트 수신은 포함되지 않습니다. Nginx HIT에 남은 이전 앱 시간은 현재 단계 분석에서 제외했습니다.
- 아래 단계 시간은 서로 중첩되고 표본 수도 다릅니다. 더하거나 독립적인 p95끼리 빼서 네트워크 시간을 만들지 않습니다.

## 병목을 구분해 읽기

### 1. 현재가·재무 재생성보다 revision 확인 대기가 길었던 구간

첫 시험의 상세 후속 2차 배치(13:25:36~37 UTC)는 100건 전부 EXPIRED였습니다. 앱 p95 882.52ms 중 `revision_wait` p95가 771.04ms였습니다. `revision_db` 6개 계측 표본의 p95는 707.75ms였습니다. 반면 `selected_read` p95는 0.05ms, 응답 잠금 대기는 0ms였고 응답 재생성은 없었습니다. 캐시를 직접 검사한 24회 모두 내부 응답 HIT였습니다.

바로 다음 상세 배치는 `revision_db` p95 35.88ms·앱 p95 160.22ms로 회복했습니다. 수집 중지 시험에서도 검색 후속 2차 배치에 `revision_db` 6개 표본 p95 755.67ms·`revision_wait` 797.39ms가 나타났습니다. 수집기를 멈췄다는 사실만으로 해당 정체가 제거되지는 않았습니다.

현재 `revision_db`는 연결 풀 checkout, SQL 실행, 결과 수신과 일부 projection 상태 확인을 함께 포함합니다. **순수 PostgreSQL 실행시간 또는 연결 풀 고갈로 확정할 수 없습니다.** 당시 DB wait event·실행계획·I/O·풀 점유율은 이 파일에 없습니다.

### 2. 앱 밖 지연도 독립적으로 존재

첫 시험의 후속 Nginx HIT는 검색 p95 298.73ms, 상세 294.29ms였습니다. 현재 경로에서 검색 목표 300ms의 여유가 작았다는 관찰이며 영구적인 네트워크 하한을 증명한 것은 아닙니다.

수집 중지 시험에서는 검색 후속 3차 배치가 **100건 모두 HIT인데 p95 1,641.63ms**였습니다. 이 배치의 지연을 FastAPI의 현재 재무 계산이나 DB revision 확인 탓으로 돌릴 수 없습니다.

수집 중지 시험의 1.6초 뒤 배치는 앱 p95가 검색 166.07ms·상세 184.39ms였지만, 본문 수신 p95가 각각 962.91ms·919.23ms였습니다. 첫 시험 본문 p95 2~4ms와 다른 현상입니다. 프록시·네트워크·클라이언트 수신 및 스케줄링을 분리할 증거가 없으므로 이를 전부 네트워크 RTT라고 부르지 않습니다.

### 3. 최초 검색의 경량 조회·공유 실행 대기

첫 시험 최초 검색의 `response_build` 10개 표본 p95는 746.68ms, 수집 중지 시험은 2,534.85ms였습니다. 후자의 `executor_wait` p95도 2,128.68ms였습니다. 검색 결과 행 조립 자체는 각각 0.96ms·1.14ms였습니다. 전체 경량 맵 조회·단일 잠금·DB 대기·실행기 대기는 현재 계측에서 더 세분화되지 않습니다. 대형 재무 JSON의 브라우저 렌더링이 원인이라고 추정해서는 안 됩니다.

## 코드와 연결한 판단

- `app.py`의 검색은 실제 revision을 확인한 뒤 같은 질의의 동시 요청을 합칩니다. `search_view.py`는 전체 상세 대신 검색용 필드만 읽고 최종 최대 30개 종목을 hydrate합니다. 하지만 quotes/enriched 전체 revision이 바뀌면 경량 맵 재구성이 필요합니다.
- 상세 요약은 종목별 quote/enriched revision을 사용합니다. 캐시 HIT에서도 revision 확인·종목 조회 검증·서명이 필요하지만 후속 `selected_read`가 0.03~0.08ms인 이번 표본에서 해당 계산을 주 병목으로 볼 근거는 없습니다.
- `RevisionReadBatcher`는 같은 이벤트 루프 차수의 요청을 합칩니다. 첫 시험 상세 후속 2차의 revision join은 94회로, 100건이 각각 독립 SQL을 보낸 형태는 아닙니다.
- `Store.request`는 응답 본문 뒤에 수집 요청을 기록하고 같은 종목을 30초 동안 합칩니다. 실제 쓰기 대기 계측은 없으므로 이 경로가 전체 지연을 만들었다고 단정하지 않습니다.
- 원천 날짜와 현재가 검증 시각을 늘리거나 캐시 만료를 늦춰 목표 수치만 맞추지 않습니다.

추가 시험은 배포 전송·복원·색인 작업과 분리하고 같은 캐시·연결 조건을 기록해야 합니다. 이번 요청에서는 추가 코드 수정이나 재측정을 하지 않았습니다. 수집 중지 성능 개선, 10배 향상, 성능 목표 통과, 전체 서비스 완료 중 어느 것도 선언하지 않습니다.
