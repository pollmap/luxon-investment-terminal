# v53 — 검색 계산 재사용·요약 의존성 분리와 공개 부하 재측정

공개 버전 `20261004-read-reuse-v53`. 토스 수집·원본·공개 주소·프런트·사용자 설정을 유지했다.

## 변경

검색은 전체 종목을 탐색할 때마다 같은 종목명·코드·별칭의 공백 제거·대소문자 정규화·한글 초성을 반복 계산하고 있었다. 문자열 내용으로 식별하는 최대 16,384개 LRU 캐시를 적용했다. 종목명이나 별칭이 바뀌면 다른 캐시 키를 사용한다. 가격·검색 응답을 이 문자열 캐시에 넣지 않으며 실제 데이터 버전 확인과 기존 요청 병합은 유지한다.

상세 요약 응답의 의존성에서 큰 `detail:{code}`를 제거했다. 이미 분리한 `detail-summary:{code}`에 회사 소개·요약 실적 변경이 반영되므로 수급 이력만 바뀌었을 때 요약을 압축·직렬화할 필요가 없다. 종목 목록·시세·요약·수집 상태의 버전 확인은 유지한다. 원본 수급과 전체 상세 API는 변경하지 않는다.

## 기능 검증

관련 검색·요약·동시 요청·기존 상세 테스트 50개 통과. 수급만 변경 → 같은 요약 재사용, 회사 소개 변경 → 즉시 새 요약 제공을 검사했다. 종목명·별칭 변경, 초성·공백·영문 검색과 시세 변경 반영도 검증했다.

가상 종목 2,875개×검색어 10개 문자열 계산 비교에서 결과 수는 동일하고 이전 171.12ms, 수정 44.72ms였다. 가상 자료 CPU 시험이며 실제 서비스 전체 속도 개선 배수로 사용하지 않는다.

## 공개 100동시 재측정

동일 Windows PC·공개 호스트에서 HTTP/2 TLS 연결 하나에 100동시 스트림을 사용했다. 검색어 10개·종목 10개, 첫 100회·이어지는 300회·1.6초 대기 후 100회를 각각 요청했다. 전후 각각 1,000회이며 오류 0건. 독립 100명의 TLS 연결 시험은 아니다.

| 대상·구간 | 수정 전 p95 | 수정 후 p95 |
|---|---:|---:|
| 검색 첫 요청 | 1,386.52ms | 2,260.71ms |
| 검색 연속 요청 | 1,858.67ms | 1,085.88ms |
| 검색 1.6초 후 | 1,429.47ms | 1,347.76ms |
| 상세 요약 첫 요청 | 1,688.82ms | 2,812.81ms |
| 상세 요약 연속 요청 | 1,676.11ms | 1,711.46ms |
| 상세 요약 1.6초 후 | 2,175.70ms | 2,858.85ms |

검색 연속 요청의 관측치는 낮아졌지만 첫 요청은 악화했고 상세 목표도 개선됐다고 판단할 수 없다. 서버 앱 헤더 처리의 연속 요청 p95 관측은 검색 1,254.61→295.90ms, 상세 239.52→298.23ms였다. 캐시 HIT/EXPIRED 비율·공개 네트워크·동시 수집 부하가 다르므로 한 쌍의 시험만으로 인과적 개선을 주장하지 않는다. 서버 헤더 시간은 전체 인터넷 응답 시간이 아니다.

검색 300ms·상세 500ms 목표는 **미달**이다. 코드를 최적화했다는 이유로 완료 처리하지 않는다. 후속 작업은 서버 부하와 인터넷/캐시 지연을 함께 줄여야 한다.

근거: `work/remaining-v53/before.json`, `after.json`, `cpu.json`, `tests.xml`, `health.json`. 변경 파일: `models.py`, `app.py`, `tests/test_search_tokens.py`, `tests/test_detail_response_cache.py`.
